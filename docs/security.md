# قلم | QALAM — الأمن

آخر تحديث: المرحلة ١ (Security & Foundation).

هذا المستند يصف الضمانات الأمنية القائمة فعلًا في الكود، وما لم يُنفَّذ بعد.
كل ادّعاء هنا مقابله اختبار أو ملف يمكن مراجعته.

---

## ١. نموذج التفويض

**القاعدة:** إخفاء زر في React ليس تفويضًا. كل قيد فعلي مفروض في PostgreSQL.

| الطبقة | ما تفرضه |
|---|---|
| PostgreSQL RLS | `auth.uid() = user_id` على كل جدول يملكه المستخدم |
| صلاحيات الجداول | `revoke` صريح للجداول الإعدادية عن `authenticated` |
| دوال `security definer` | العمليات التي تحتاج امتيازًا، مقيّدة بـ `auth.uid()` ولا تقبل معرّف مستخدم من العميل |
| دالة Netlify | المصادقة قبل أي عمل؛ المفتاح السري لا يغادر الخادم |

**اعتماد ضمني مهم:** الهجرات لا تحتوي `grant` صريحًا لدور `authenticated`؛
المشروع يعتمد على الصلاحيات الافتراضية التي يضبطها Supabase لمخطط `public`.
لذلك كل جدول جديد يُنشأ في `public` **يُمنح تلقائيًا** لـ `authenticated`،
و`revoke` الصريح في `0006` ضرورة لا تجميل.

## ٢. حد المعدّل (Rate Limiting)

**قبل المرحلة ١:** عدّاد في ذاكرة الدالة. دوال Netlify عديمة الحالة وتُنشأ منها
نسخ متوازية، فالعدّاد لم يكن يحمي شيئًا عمليًا.

**الآن:** الحد دائم وذرّي في قاعدة البيانات.

- `public.begin_ai_request()` — يحجز قبل التنفيذ، ويقفل لكل مستخدم بـ
  `pg_advisory_xact_lock` **قبل** العد، فلا تتجاوز الطلبات المتزامنة الحد.
- `public.finish_ai_request()` — يحسم الصف المحجوز.
- `netlify/functions/_shared/rateLimit.ts` — حاجز محلي رخيص فقط، ليس حدًّا.

ثلاث طبقات، كلها قابلة للضبط في `app_settings` **بلا نشر جديد**:

| المفتاح | الافتراضي | الغرض |
|---|---|---|
| `burst_per_10s` | 6 | اندفاع لحظي |
| `per_minute` | 20 | النافذة المنزلقة |
| `per_day` | 200 | سقف يومي لكل مستخدم |

```sql
update public.app_settings
   set value = jsonb_set(value, '{per_day}', '500')
 where key = 'ai_rate_limits';
```

كل رفض يُرجع `429` مع رأس `Retry-After`.

**سلوك عند تعذّر القاعدة:** يُسمح بالطلب (fail-open) ويُسجَّل `ai.quota_check_failed`.
إسقاط كل الطلبات لأن عدّاد الحد متعذّر يحوّل خللًا جزئيًا إلى انقطاع كامل،
والمصادقة — وهي الحاجز الأمني الفعلي — تحققت قبل هذه النقطة.

## ٣. تتبّع الاستخدام والخصوصية

`ai_requests_metadata` بيانات وصفية **فقط**. لا عمود فيه يقبل نص مراسلة،
ويوجد اختبار يفشل إن أُضيف عمود باسم `body` أو `prompt` أو `content` أو `text`
أو `subject`.

يُسجَّل: المستخدم، المهمة، المزوّد، النموذج، الحالة، المدة، عدد الرموز، رمز خطأ قصير.

الجدول **غير قابل للتعديل من المتصفح**: لا سياسة `UPDATE`، والحسم يمر بدالة
تقصر التحديث على صف المستخدم نفسه وعلى الحالة `pending` — فلا يُعاد كتابة سجل محسوم.

### سياسة السجلات

`netlify/functions/_shared/log.ts` هو المسار الوحيد للكتابة في السجل.
لا تقبل الوحدة نصًا حرًّا: اسم الحدث من مجموعة مغلقة، والحقول أعداد أو منطقيات
أو رموز قصيرة. تُحجب تلقائيًا: مفاتيح `sk-`، رموز JWT، رؤوس `Bearer`، البريد
الإلكتروني، وأي نص متعدد الأسطر أو أطول من ٦٤ محرفًا.

**ممنوع تمامًا في السجل:** محتوى المراسلة، الـprompt، المراسلة الواردة، المرفقات،
رموز الجلسة، مفاتيح API، ورسالة الخطأ الخام من المزوّد.

جسم استجابة الخطأ من OpenAI **لا يُقرأ إطلاقًا** — قد يردّ صدى الـprompt.
يُصنَّف رمز الحالة إلى رمز قصير فقط (`upstream_auth`, `upstream_rate_limited`, …).

في المتصفح: `ErrorBoundary` يسجّل رسالة الخطأ في التطوير فقط. رسالة خطأ React قد
تحمل محتوى مُمرَّرًا للعرض، فيُكتفى في الإنتاج بنوع الخطأ ومسار المكوّنات.

## ٤. السقف الزمني

كل استدعاء خارجي محدود بمهلة عبر `AbortController`:

- OpenAI: `AI_TIMEOUT_MS` (افتراضي 45s، يُقصر داخل [5s, 120s])
- إجراءات Supabase: 8s ثابتة

انتهاء المهلة مُميَّز عن إلغاء المستخدم وعن خطأ المزوّد، ويعيد `504` برسالة مفهومة.

## ٥. رؤوس الأمان و CSP

في `netlify.toml`. الـCSP مبنية على ما يحتاجه البناء فعليًا — لا تخمين:

- `script-src 'self'` بلا `unsafe-inline` ولا `unsafe-eval` (Vite لا يُخرج سكربتًا مضمّنًا)
- `style-src` تحتاج `'unsafe-inline'` لخاصية `style={{…}}` في React
- `connect-src` محصورة في Supabase — لا يمكن للصفحة إرسال بيانات إلى مستضيف آخر
- `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`

**تضييق ممكن لاحقًا:** `connect-src` تستخدم `https://*.supabase.co` لأن `netlify.toml`
ملف ثابت لا يقرأ متغيرات البيئة. لحصره في مشروع واحد يلزم توليد ملف `dist/_headers`
في خطوة بناء تقرأ `VITE_SUPABASE_URL`. لم يُنفَّذ: المكسب صغير مقابل خطوة بناء إضافية،
والحماية الأساسية (منع المستضيفات الأخرى) محفوظة.

**الميكروفون:** مُغلق الآن عن قصد (`microphone=()`). المرحلة ٦ (Voice AI) تحتاج
`microphone=(self)` — تغيير سطر واحد في `Permissions-Policy`، ولا يمس الـCSP لأن
الصوت لا يضيف مستضيفًا خارجيًا.

## ٦. سياسة التسجيل

`app_settings.signup.mode` تقبل `public` (الافتراضي) أو `invite_only`.

في وضع الدعوة، المُشغّل `handle_new_user` يرمي استثناءً إن لم توجد دعوة صالحة،
فيُلغى إدراج `auth.users` بالكامل ولا يبقى أثر لحساب مرفوض. الدعوة تُستهلك مرة
واحدة، والمطابقة بلا حساسية لحالة الأحرف، وتُرفض المنتهية والملغاة.

```sql
-- تفعيل وضع الدعوة
update public.app_settings set value = '{"mode":"invite_only"}' where key = 'signup';
-- إضافة دعوة
insert into public.signup_invites (email, expires_at)
values ('someone@example.com', now() + interval '14 days');
```

### ⚠️ MANUAL ACTION REQUIRED — إغلاق التسجيل فعليًا

بوابة القاعدة أعلاه تمنع إنشاء الحساب، لكن Supabase Auth يقبل الطلب أولًا ثم
يفشل. لإغلاق التسجيل عند الباب الخارجي أيضًا (دفاع في العمق):

1. افتح Supabase Dashboard → **Authentication** → **Sign In / Providers**
2. أوقف **Allow new users to sign up**
3. لدعوة مستخدم: **Authentication** → **Users** → **Invite user**

هذا إعداد لوحة تحكم خارج المستودع — **لم يُنفَّذ من الكود ولا يمكن تنفيذه منه.**

`signup_invites` و`app_settings` محجوبان عن المتصفح حاليًا؛ إدارتهما من SQL Editor.
واجهة إدارة الدعوات تأتي مع الأدوار في **المرحلة ٢**.

## ٧. Service Role

`service_role` **غير مستخدم في أي مكان**. حد المعدّل والتتبّع يستدعيان إجراءات
القاعدة برمز جلسة المستخدم نفسه ومفتاح `anon` — فلا تستطيع الدالة رؤية ولا تعديل
بيانات مستخدم آخر حتى لو أُصيبت بخلل. اختبار ساكن يفشل إن ظهر `SERVICE_ROLE`
في كود المتصفح أو كود الخادم.
